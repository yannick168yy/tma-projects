# 包网（白标多租户）架构方案

> 状态：设计定稿，待实施
> 分支：`feature/whitelabel-multitenant`
> 决策日期：2026-09-02

## 0. 已拍板的决策

| # | 决策项 | 结论 |
|---|--------|------|
| 1 | 隔离方案 | **每租户独立 schema**（`betogo_t{NNN}`）+ 平台库 `betogo_platform`，共用一套代码与一个应用集群 |
| 2 | 资金流 | **两种模式都要支持**：平台统一代收代付 / 租户自带通道，且可在同一租户内混用 |
| 3 | 分成模式 | **四种可组合**：充值金额抽佣、GGR 分成、有效流水提成、固定月费+保底 |
| 4 | 定制化 | 分四层承接（配置 → 区块 → overlay → 私有模块），主干代码禁止出现租户 if 分支 |
| 5 | 开发方式 | 独立分支长线开发，自营站作为 tenant #1 平滑迁入 |

## 1. 术语与命名

- **租户 / 运营商（tenant / operator）**：包网客户，拥有独立域名、独立用户与资金、独立后台。
- **市场（market）**：PH / ID 等地区维度，**与租户正交**，一个租户可同时运营多个市场。
- **站内代理（agent）**：现有 `bg_agent_domain` / `bg_user_agent` 的推广代理，属于租户内部概念，**与租户不是一回事**，代码与文案都不得混用命名。

代码统一用 `tenant`，中文统一用"运营商"。

## 2. 隔离架构

### 2.1 数据库

```
betogo_platform     平台库：租户、域名、套餐、计费、账单、跨租户风控、平台 BI
betogo_t001         自营站（现有 betogo 库改名或映射）
betogo_t002 ...     每个包网客户一个库，表结构与主干迁移完全一致
```

租户库表结构**永远保持一致**，不允许某租户单独加表；租户差异只走配置与 overlay（见第 6 节）。

### 2.2 请求路由（核心改造点）

现状：`apps/bff-node/src/clients/mysql.client.ts:20` 的 `getMysqlPool(env)` 是全局单例，
BFF 全部 SQL 都经这一个入口；core-node 同理在 `apps/core-node/src/plugins/mysql.ts:12`。

改造：
1. 新增 `tenant-context.ts`，用 `AsyncLocalStorage` 保存 `{ tenantId, tenantCode, market }`。
2. 新增租户解析中间件（在 requestId 之后、鉴权之前）：`Host` → 平台库 `tenant_domain` → 租户；
   缓存在 Redis（TTL 300s，与现有 `site-domain.service.ts` 同样的降级策略）。
3. `getMysqlPool()` 改为从 ALS 取租户，按 `tenantCode` 缓存连接池（LRU，闲置回收）。
4. core-node 回调入口没有 Host 可依赖 → 回调 URL 里带租户段（`/callback/:tenantCode/...`），
   或用聚合商子代理号反查租户。

**业务代码与 SQL 一行不用改** —— 这是选分库方案最大的收益。

### 2.3 Redis（🔴 上线前必须先做）

现状无 `keyPrefix`，键形如 `wallet:balance:{userId}`。分库后各租户 userId 会重号，
不加前缀就是**跨租户余额串号**的资金事故。

改造：所有 Redis 键统一加 `t{tenantId}:` 前缀，覆盖钱包余额、会话、回调幂等键、分布式锁、
限流计数、各类缓存。用 ioredis 的 `keyPrefix` 按租户建实例，或统一走一个 `key()` 包装函数
（推荐后者，便于扫描遗漏）。

### 2.4 定时任务

现状 `apps/bff-node/src/app.ts:71-199` 有 20+ 个全局 `setInterval`（结算、返水、VIP、社区、播报…），
已有 `BFF_DISABLE_SINGLETON_JOBS` 做多实例去重。

改造：
- 每个 job 改成"遍历已启用租户 → 在租户上下文里执行"。
- 业务日切按**租户 × 市场**的时区（沿用 `207_team_market_timezone.sql` 的逻辑）。
- 分布式锁 key 带租户；单租户失败不影响其他租户（逐租户 try/catch + 告警）。
- 租户数上来后，改为任务队列分发，避免单实例串行跑 N 个租户超时。

### 2.5 迁移与备份

- 迁移执行器改为：读平台库租户列表 → 逐库执行未应用的迁移 → 汇总报告；
  新库要能从 `001` 一路跑到最新（当前 217）。
- 迁移失败必须**中止部署**并明确指出是哪个租户库，禁止跳过继续。
- 备份按库粒度，租户可申请数据导出（也是退出机制的一部分）。
- CLAUDE.md 里"禁止在迁移文件写 TRUNCATE/DELETE"的铁律**加倍适用**：一条脏迁移现在会清空 N 个租户。

### 2.6 消息与其他

- NATS subject 加租户段：`tenant.{code}.wallet.ledger`。
- 日志与 trace 全链路带 `tenantCode` 字段。
- 对象存储路径按租户前缀隔离。

## 3. 平台库 schema 草案

| 表 | 用途 |
|---|---|
| `pf_tenant` | 租户主体：code、名称、状态（试用/正常/欠费停站/关站）、库名、创建时间 |
| `pf_tenant_domain` | 域名 → 租户 + 市场 + 用途（主站/App线路/落地页）、证书状态 |
| `pf_tenant_market` | 租户开通的市场与币种、时区 |
| `pf_plan` / `pf_tenant_plan` | 套餐与功能开关矩阵（feature flags）、可覆盖配置白名单 |
| `pf_tenant_provider` | 聚合商子代理账号（win568 agent）、密钥（加密存储） |
| `pf_payment_channel` | 平台自营通道池（模式 A 用） |
| `pf_tenant_channel` | 租户启用的通道：来源 platform / tenant、费率、开关 |
| `pf_billing_plan` / `pf_billing_rule` | 分成规则（见第 5 节） |
| `pf_billing_daily` | 每日计费快照（充值额、GGR、有效流水、活动成本、佣金成本） |
| `pf_invoice` / `pf_invoice_item` | 结算单与明细 |
| `pf_tenant_account` / `pf_tenant_ledger` | 租户额度账户：押金、授信、应收应付、流水（不可变） |
| `pf_risk_blacklist` | 跨租户黑名单：设备指纹、银行卡、手机号、IP |
| `pf_admin` / `pf_admin_role` | 平台管理员与角色 |
| `pf_audit_log` | 平台操作审计，含 impersonate（以租户身份登录）全程留痕 |
| `pf_bi_daily` | 各租户库抽数汇总，供平台总览（**不做实时跨库 UNION**） |

## 4. 资金流双模式

`pf_tenant_channel.owner` 区分来源，同一租户可混用，前台按统一列表展示。

**模式 A：平台统一代收代付**
- 通道凭据在平台库，资金进平台账户。
- 玩家充值 → 平台账户；租户在 `pf_tenant_account` 上记应付。
- 玩家提现 → 平台放款，从租户额度扣减；**额度不足时按套餐策略拒绝或走人工**。
- 租户需缴押金/授信额度，欠费自动降级（先停提现、再停充值、最后停站）。
- 平台承担资金与合规压力，抽水高。

**模式 B：租户自带通道**
- 通道凭据存租户库（加密），资金直接进租户自己的账户，平台不碰钱。
- 平台只依赖回调入库的流水做计费 → **必须保证回调统一经平台网关落库**，否则分成无据可查。
- 适合有自己支付资源的大客户，费率低。

设计要点：`deposit_order` / `withdraw_order` 增加 `settlement_mode` 字段，记录该笔走的是哪种模式，
账单与对账按此拆分，避免混用时算不清。

## 5. 计费 / 分成引擎

一个 `billing_plan` 由多条 `billing_rule` 组合，规则类型：

| type | 计费基数 | 常用参数 |
|---|---|---|
| `deposit_commission` | 成功充值金额 | 费率、分档 tier、是否扣除失败/退款 |
| `ggr_share` | GGR | 费率、`deductBonus`、`deductCommission`、负数结转 `carryOver` |
| `turnover_rebate` | 有效投注流水 | 费率、分场馆（棋牌/电子/体育）差异化 |
| `monthly_fee` | 固定 | 月费金额、保底额（`max(月费, 分成)` 或 `月费 + 超额分成`） |

**GGR 口径必须写死，这是包网最容易扯皮的地方：**

```
GGR = 有效投注 - 派彩              （纯输赢净额）
净收益 = GGR - (deductBonus ? 活动成本 : 0) - (deductCommission ? 团队佣金 : 0) - 通道手续费(仅模式A)
```

默认口径：`deductBonus=true, deductCommission=true, carryOver=true`（负 GGR 结转下月），
签约时逐租户在 plan 上确认，账单页面把每一项都列出来，不给争议留空间。

结算流程：日切写 `pf_billing_daily` 快照（**快照后不可变**，规则改动只影响未来）→
周期末生成 `pf_invoice` → 租户在后台确认 → 平台核销 → 走额度账户扣划。

## 6. 定制化分层（关键：如何在不烂掉主干的前提下接定制）

### 铁律
> **主干代码永远不出现 `if (tenant === 'xxx')`。**
> 所有租户差异必须落在下面四层之一，越靠上越优先。

**L1 配置化（目标覆盖 80% 需求）**
- 主题变量：主色/圆角/字体/暗色，一套 CSS 变量下发。
- 品牌资产：logo、启动图、App 图标、站名、客服入口。
- 文案包：i18n 覆盖层，租户可改任意 key。
- 首页布局：现有 `192_homepage_section_visibility` / `201_home_content_localized_images`
  已经是这条路，扩展成"区块 + 排序 + 参数"的 JSON schema。
- 功能开关：套餐 feature flags 控制模块可见性（体育/棋牌/彩票/团队/VIP/签到…）。
- 业务参数：活动数值、返水比例、提现规则、风控阈值（按套餐限定可改范围）。

**L2 区块注册表（覆盖 15%）**
- 前端建立"区块组件注册表"，首页/活动页/个人中心由租户配置选区块、定顺序、传参。
- 新区块进公共库，**所有租户可选**，不做私有区块。
- 后台同理：菜单与报表列由配置驱动。

**L3 租户 overlay（覆盖 5%，付费定制）**
- 目录 `apps/web-tma/src/tenants/<code>/`，构建时按租户 code 做 Vite alias 覆盖同名组件/样式/文案。
- 出包：`--tenant=t007` 走独立构建产物与独立 CDN 前缀。
- 主干组件保持不变，overlay 只允许覆盖，不允许修改主干。
- 代价：该租户升级时需回归 overlay，签约时按"定制维护费"计价。

**L4 私有模块（例外，需平台审批）**
- 只对大客户开放，必须封装成独立模块并通过约定接口挂载，禁止侵入核心链路（钱包/注单/风控）。
- 后台深度定制优先引导走**平台开放 API + 租户自建系统**，而不是改后台代码。

### 版本策略
- **强制跟随主干**，不做多版本并存（否则 N 个租户 = N 个维护分支，必崩）。
- 新功能默认关闭，靠 feature flag 灰度到指定租户。
- overlay 租户在主干发版时跑一次针对性回归。

## 7. 开站流水线（一键开站）

1. 平台后台提交开站申请 → 审核
2. 建库 `betogo_t{NNN}` → 跑全量迁移 → 灌种子配置（继承套餐默认值）
3. 注册域名 → 泛域名解析 + 自动证书（Caddy/ACME）→ 写 `pf_tenant_domain`
4. 调 win568 `registerAgent`（`apps/core-node/src/clients/win568.client.ts:65`）建子代理，密钥入平台库
5. 配置支付通道（模式 A 直接继承平台池 / 模式 B 录入租户凭据）
6. 生成 App 包：复用现有 `app_domain_groups` + `route-health` + 路由签名机制，参数化包名/图标/线路组
7. 冒烟自检：注册 → 充值 → 进游戏 → 提现 全链路自动化跑一遍，通过才放行

目标：**从审核通过到可访问 < 30 分钟，全自动无人工 SSH。**

## 8. 路线图

### P0 单租户化（对外零变化，最关键）
- 平台库 + `pf_tenant` / `pf_tenant_domain`，自营站落为 tenant #1
- 租户解析中间件 + ALS 上下文 + 连接池按租户路由（BFF & core-node）
- **Redis 全量加租户前缀**
- 定时任务改为遍历租户 + 按租户市场时区切业务日
- 迁移执行器支持多库
- NATS subject / 日志 / 对象存储加租户维度
- **验收**：线上功能表现完全不变；跨租户越权测试全绿（见第 9 节）

### P1 开站能力
- 开站流水线（第 7 节）
- 品牌与主题运行时下发（`web-tma/src/config/market.ts` 的编译期域名表退化为兜底，不再是真相源）
- 平台控制台：开站/停站/impersonate/租户列表
- L1 配置化第一批：主题、logo、文案、首页区块、功能开关

### P2 商务闭环
- 计费引擎四种规则 + 日切快照 + 账单
- 租户额度账户、押金授信、欠费自动停站
- 双资金模式落地（模式 A 的平台代付放款链路）
- 平台总览 BI

### P3 生态
- 租户自助：通道自配、活动模板、App 自助出包
- L2 区块注册表 + L3 overlay 构建流水线
- 跨租户风控联防（同设备/同卡/同 IP 撞库识别）—— 包网平台真正的护城河
- 开放 API、多聚合商

## 9. 风险与红线

**资金隔离测试清单（P0 验收必须全绿，每条都要有自动化用例）**
- [ ] 用 tenant2 的 token 访问 tenant1 的用户/订单/钱包 → 全部 404/403
- [ ] 两租户存在相同 userId 时，余额、会话、幂等键互不影响
- [ ] 聚合商回调带 tenant1 的注单打到 tenant2 → 拒绝且告警
- [ ] 定时结算只影响本租户数据，跨租户金额零变动
- [ ] 平台管理员 impersonate 后的所有写操作有审计记录
- [ ] 租户后台无法读到平台库与其他租户库（DB 账号按库授权，不给全局权限）

**其他红线**
- P0 改动直接动线上资金链路（Redis 键、定时结算），**必须在阿里云测试站跑足回归**；
  生产部署按 CLAUDE.md 铁律，等用户逐次明确授权。
- 迁移文件禁止任何形式的全表清理 —— 现在一条脏迁移会清空所有租户。
- 租户 DB 账号只授权自己那个库；平台库凭据不下发给任何租户侧组件。
- 第三方通道凭据、聚合商密钥一律加密存储，后台只显示掩码。

## 10. 待确认

1. 自营站 tenant #1 迁移方式：现有 `betogo` 库改名，还是保留库名只在平台库登记映射？（后者风险更小，推荐）
2. 目标租户规模量级（10 / 50 / 200+）？超过 ~50 个库时，定时任务要提前改队列分发，DB 也要考虑分实例。
3. 租户后台是共用一套 web-admin（按域名/登录态区分），还是平台后台与租户后台分成两个应用？
4. 模式 A 下租户额度不足时的默认策略：拒绝提现 / 平台垫付 / 转人工。
