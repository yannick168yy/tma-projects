# BI 数据分析模块 — 详细方案

> 2026-07-20 起草，待用户确认后分期实施。
> 目标：让运营打开后台 1 分钟内看清「现在怎么样、哪里不对劲、下一步该干什么」。

## 0. 设计原则

1. **不引入外部 BI 系统**。MySQL 日聚合表 + core-node cron + web-admin 页面（antd + echarts），全部复用现有技术栈。
2. **分析查询绝不扫 OLTP 明细表**。所有页面只读 `bi_*` 聚合表，速度恒定，不拖累线上交易。
3. **预测 = 统计外推 + 规则评分**，不是机器学习。当前数据量下，加权移动平均、cohort 曲线外推、RFM 评分的效果与可解释性远好于黑盒模型，且零额外依赖。
4. **每个「发现问题」的功能都要接一个「采取行动」的出口**：圈出流失风险用户 → 一键发 TG 推送 / 发复充优惠；发现 RTP 异常 → 一键跳转注单核查。分析不落地到动作就是摆设。

## 1. 数据底座：预聚合表

core-node 新增 `bi-aggregate.cron.ts`，每天 01:00（Asia/Manila）聚合前一天数据；当天数据每 10 分钟增量刷新。全部 `INSERT ... ON DUPLICATE KEY UPDATE`，幂等可回填。

| 表 | 主键 | 内容 |
|---|---|---|
| `bi_daily_platform` | (stat_date, currency) | 充值/提现额与笔数、有效投注、派彩、GGR、活动成本(彩金+返水+spin+任务)、支付手续费、NGR、DAU、投注人数、新增注册、首充人数、首充金额 |
| `bi_daily_provider` | (stat_date, provider, currency) | 注单数、投注人数、投注额、派彩、GGR、实际 RTP |
| `bi_daily_game` | (stat_date, game_key) | 投注额、派彩、GGR、独立玩家、注单数、启动次数(launch_history) |
| `bi_daily_user` | (stat_date, user_id, currency) | 投注额、盈亏、充值、提现、领取彩金、投注笔数 |
| `bi_daily_acquisition` | (stat_date, entry_source) | 新增注册、首充人数、首充额、拉新成本(试玩金/下载奖/首充彩金) |
| `bi_user_score` | (user_id) | churn_score、rfm 分层、预测 LTV、个人投注节奏、最近活跃日 — 每日全量重算 |
| `bi_target` | (period, metric) | 运营设定的月度目标值 |
| `bi_alert` | (id) | 异常告警：类型、维度、当前值、基线值、偏离度、状态 |

维度口径澄清（2026-07-20 用户确认）：
- **游戏商 = 游戏厂商层面（JILI、PG Soft、Pragmatic Play…）**，即 `bg_568win_game.provider`（134 已规范化），不是聚合商 568win。注单归因到厂商必须用 **(gpid, provider_id) 复合键** join `bg_568win_game` 的主键 (game_provider_id, game_id)——只用 provider_id(=GameId) 不唯一，这是历史坑。
- **渠道 = 入口域名或 tma**，直接用现有 `bg_user.register_entry_source`（注册归因）与 `bg_login_log.entry_source`（当日活跃归因）。两套口径：拉新/首充/LTV 按注册域名终身归因；DAU 按当日登录域名归因。

已知坑（必须遵守）：
- 游戏品类只能取 `bg_turnover_logs.sort_category`；单独 `provider_id` = GameId 不唯一，join 游戏表必须带 gpid。
- 多币种分币种聚合存储，展示层用汇率表折算 PHP 合计；USDT/USDC 走 USD agent 1:1。
- 统计日边界 Asia/Manila。

## 2. 功能模块

### A. 运营驾驶舱（首页，替换现有简陋 Dashboard）

回答「现在怎么样」：
- **今日实时卡片**：GGR、NGR、充值、提现、DAU、新增、首充转化率——每个数字带「vs 昨天同时刻」「vs 上周同日」的涨跌幅，红绿标注。
- **核心趋势图**：GGR/NGR/充提/DAU 折线，近 30/90 天，日/周/月粒度。
- **目标进度条**：读 `bi_target`，展示本月 GGR、新增、首充目标的完成率 vs 时间进度率；差距换算成「剩余天数每天需要做到 X」的 run-rate 提示。
- **异常告警栏**：读 `bi_alert` 未处理告警，点击直达对应分析页。
- **7 日预测**：GGR 与充值的未来 7 天预测带（见 §3.1），叠加在趋势图尾部。

### B. 游戏商分析

回答「该跟哪家游戏商谈、哪家有问题」：
- 各 provider 流水/GGR/RTP/玩家数对比表 + 趋势图，支持币种筛选。
- **RTP 异常预警**：某 provider 当日 RTP 偏离其自身 28 天基线 ±N 个标准差 → 写入 `bi_alert`（可能是游戏商结算错误、玩家套利或黑客行为）。
- 游戏商集中度：流水占比饼图——单一 provider 占比过高提示供应商风险。
- 关联 `provider_balance_snapshot`：各 agent 账户资金占用 vs 产出 GGR 的效率。

### C. 游戏分析

回答「首页该推什么游戏、哪些游戏白占位置」：
- Top 游戏排行（流水/GGR/玩家数/人均流水），品类占比（sort_category）。
- **点击→下注转化率**：`bg_game_launch_history` 启动数 vs 实际产生注单的玩家数。转化低 = 封面吸引人但游戏不行，高流水低曝光 = 该加推。
- 游戏留存：玩过某游戏的玩家 7 天内是否回来再玩，识别「留人」的游戏。
- 新上架游戏追踪：上架 14 天内的表现榜，快速决定推还是撤。
- 首页栏目效果：对照 homepage_section 配置位与实际产出，指导运营调整首页。

### D. 用户分析

回答「用户从哪来、值多少钱、在哪一步流失」：
- **转化漏斗**：注册 → KYC → 首充 → 复充（二充）→ 30 日留存，可按 entry_source 拆分对比。
- **留存 cohort 表**：按注册周分组的 D1/D3/D7/D14/D30 留存（登录口径 + 投注口径两套）。
- **LTV 曲线**：各 cohort 的累计 NGR/人 随时间的曲线；新 cohort 按历史曲线形状外推 D90 LTV（见 §3.3）。
- **RFM 分层**：按 充值最近度/频次/金额 分成 大R/中R/小R/流失中/已流失，各层人数与 GGR 贡献占比；与现有 `bg_user_segment` 互补。
- **高盈利玩家榜**：近 7/30 天净赢排行，一键跳转风控档案。

### E. 渠道 / 拉新 / 团队

回答「拉新的钱花得值不值」。渠道 = 入口域名或 tma（见 §1 口径澄清）：
- 按注册域名：新增、首充转化率、人均拉新成本（试玩金+下载奖+首充彩金）、cohort LTV → **预估回本周期**（成本 ÷ 预测 LTV 曲线）。
- 按当日登录域名：各域名 DAU 趋势——推广新域名后立刻能看到量起没起来。
- 团队/代理维度：各团队新增、流水、佣金支出、贡献 NGR——识别「刷佣金不产出」的团队（与风控联动）。

### F. 支付通道（轻量）

- 各通道成功率、平均到账时长、手续费率趋势；成功率骤降写入 `bi_alert`。

## 3. 预测能力（详细口径）

### 3.1 营收/充值 7 日预测
按「星期几」分组的加权移动平均（近 4 个同星期日取加权均值，近期权重高），输出预测值 ± 波动带。数据不足 8 周时退化为 7 日移动平均。目的不是精确预测，而是给目标进度条提供「照目前趋势月底能到多少」的达成率预估。

### 3.2 流失预警（churn score）
每用户计算「个人投注节奏」= 近 30 天有投注日之间的平均间隔。当前静默天数 > 2× 个人节奏 → 进入风险名单；结合 RFM 衰减合成 0-100 分。
**行动出口**：风险名单页支持按 VIP 等级/历史充值筛选，一键操作：发 TG 广播（复用 tg_broadcast）、发放复充优惠（复用 redep_offer）。这是整个 BI 模块最直接产生营收的功能。

### 3.3 LTV 外推
取成熟 cohort（注册满 90 天）的平均累计 NGR 曲线形状，新 cohort 用「已观测天数的实际值 × 历史曲线放大系数」外推 D90。按渠道分别外推，用于 §2.E 的回本周期估算。

### 3.4 异常检测
统一 z-score 框架：当日值 vs 近 28 天同星期基线，|z| > 3 写 `bi_alert`。监控项：平台 GGR、各 provider RTP、各支付通道成功率、提现总额、新增注册数。告警在驾驶舱展示，可选同步推到管理员 TG 群。

### 3.5 目标管理
运营在后台设置月度目标（GGR/新增/首充人数），驾驶舱自动算：完成率、时间进度、所需日均 run-rate、按 §3.1 预测的预计达成率。让「下一步目标」从拍脑袋变成看数定。

### 3.6（可选，最后做）AI 日报
每天早上 cron 把昨日聚合数据 + 告警喂给 Claude API，生成一段中文运营日报（亮点/异常/建议），推送到管理员 TG。成本极低（每天一次调用），价值是老板不打开后台也能掌握大盘。

## 3.9 性能与数据存储（2026-07-20 用户关切，明确回答）

**BI 数据是另存的**：`bi_*` 全部是独立新表，只存按天×维度压缩后的聚合结果（每天每维度一行），不复制明细。业务明细表（注单、订单、流水）保持原样只读，BI 不在上面建任何新索引、不加任何触发器、不改任何写入路径。存储量级：每天几百行，一年不到 20 万行，可忽略。

**对日常性能的影响控制**：
1. 后台 BI 页面**只查 `bi_*` 聚合表**，毫秒级，与业务表零接触。
2. 重活（扫昨日明细做聚合）放在 **01:00 低峰期**，且查询全部走现有索引的窄时间范围扫描（`created_at` 当天区间），单次只碰一天的数据。
3. 当日 10 分钟增量刷用**水位线**（上次处理到的 id/时间），每次只扫最近 10 分钟的新行，都是索引范围小查询。
4. 聚合任务用独立的低并发连接（同现有 cron 模式），串行执行不抢连接池；任何一步失败只影响 BI 数字延迟，不影响业务。
5. 前台 web-tma 完全不感知 BI 的存在，无任何请求路径变化。
6. 若将来数据量大到聚合任务变重（日注单几十万以上），再考虑 MySQL 从库跑聚合——现在不需要，方案预留了这条升级路。

## 4. 权限与路由

- bff 新增 `/admin/bi/*` 只读路由；`bi_target` 的写入、告警状态流转需要 super_admin 或 finance。
- 流失名单的「发优惠/发广播」动作走现有模块的权限与审计日志，BI 只做入口。
